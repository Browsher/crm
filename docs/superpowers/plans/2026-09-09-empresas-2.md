# Fatia `empresas.2` — plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Dar tela à base importada: `/empresas`, com busca sem acento, busca
exata por CNPJ e paginação, tudo cortado no banco.

**Architecture:** A migração `0015` traz a maquinaria que só a busca consome —
schema `extensoes`, a extensão `unaccent`, o invólucro `IMMUTABLE` `sem_acento`
e a coluna gerada `busca`. Sobre ela, um repositório de leitura próprio (não
cópia do `listar()` de usuários) devolve uma página por vez com `LIMIT`/`OFFSET`
e `count(*) OVER ()`, e um `LEFT JOIN cep` traz cidade e UF. As telas são
componentes de servidor: a busca é um `<form method="get">`, sem JavaScript e
sem estado no cliente.

**Tech Stack:** TypeScript sem ponto e vírgula, aspas simples. Vitest (projetos
`unitario` e `integracao`). Postgres 17 no container, 18.6 na Railway. Next
16.3.4, App Router. Render testado por `renderToStaticMarkup`, sem jsdom.
**Nenhuma dependência nova.**

**Spec:** `docs/superpowers/specs/2026-09-09-empresas-design.md` — seções "Busca
sem acento", "Políticas e privilégios", "As telas" e "Testes".

## Duas correções da spec, medidas antes de escrever o plano

As duas foram conferidas no container (`postgres:17`) em 2026-09-09, num banco
descartável com um papel sem privilégio nenhum, reproduzindo a migração da spec
letra por letra. **A migração da spec, como está escrita, não funciona** — e a
falha não aparece na aplicação da migração, só na primeira consulta do gestor.

**1. Faltam dois `GRANT` para `app_usuario`.** `sem_acento` **não** é
`SECURITY DEFINER`: roda como quem chama, e quem chama é `app_usuario`. Com
`REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA extensoes FROM PUBLIC` e nada mais,
o corpo dela não alcança `extensoes.unaccent`. Medido, nesta ordem:

| Estado | `SELECT sem_acento('Iluminação São João')` como o papel |
|---|---|
| só os `REVOKE` da spec | `ERROR: permission denied for schema extensoes` |
| mais `GRANT USAGE ON SCHEMA extensoes` | `ERROR: permission denied for function unaccent` |
| mais `GRANT EXECUTE ON FUNCTION extensoes.unaccent(regdictionary, text)` | `iluminacao sao joao` |

O `INSERT` do gestor falha do mesmo jeito e pelo mesmo motivo — a expressão da
coluna gerada é avaliada com o privilégio de quem insere, não de quem criou a
tabela. Então a migração leva os dois `GRANT`, e o `GRANT EXECUTE` é **só na
assinatura de duas entradas** que `sem_acento` chama: `unaccent_init` e
`unaccent_lexize` continuam fechadas, e a `unaccent(text)` de um argumento
também. Conferido depois dos `GRANT`: a invariante de PUBLIC continua devolvendo
zero linha, porque `GRANT` para um papel nomeado não é `grantee = 0`.

**2. `ORDER BY razao_social` sozinho não pagina.** Duas empresas com a mesma
razão social deixam a ordem indefinida entre um `LIMIT`/`OFFSET` e o seguinte, e
a página 2 repete ou pula linha — que é exatamente o teste que a spec pede. O
`ORDER BY` desta fatia é `razao_social, id`.

**Um terceiro ponto, que a spec não decidiu e o plano decide:** `%` e `_` são
metacaracteres de `LIKE`. Digitar `%` na busca traria a base inteira sem o
gestor entender de onde veio. O termo é escapado em TypeScript e a consulta usa
`ESCAPE '\'` — medido: `100\%` acha só a empresa cuja razão social tem `100%`.

**Sobre a numeração na spec.** A tabela de dívida da spec e a seção sobre
`fundacao.md` dizem `empresas.1` onde o assunto é `0015`, `sem_acento` e o
índice GIN. Aquilo foi escrito antes de a `empresas.1` virar as correções da
auditoria. **Onde a spec diz `empresas.1` falando de busca, leia `empresas.2`** —
é esta fatia. A própria spec avisa que a numeração segue a ordem de execução.

```sql
-- ver docs/db/0015.md
BEGIN;
CREATE SCHEMA extensoes;
CREATE EXTENSION unaccent WITH SCHEMA extensoes;
REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA extensoes FROM PUBLIC;
GRANT USAGE ON SCHEMA extensoes TO app_usuario;
GRANT EXECUTE ON FUNCTION extensoes.unaccent(regdictionary, text) TO app_usuario;
CREATE FUNCTION sem_acento(p text) RETURNS text
LANGUAGE sql IMMUTABLE PARALLEL SAFE STRICT SET search_path = ''
AS $$ SELECT lower(extensoes.unaccent('extensoes.unaccent'::regdictionary, p)) $$;
REVOKE EXECUTE ON FUNCTION sem_acento(text) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION sem_acento(text) TO app_usuario;
ALTER TABLE empresa ADD COLUMN busca text GENERATED ALWAYS AS (sem_acento(razao_social || ' ' || coalesce(nome_fantasia, ''))) STORED;
COMMIT;
```

Três coisas que parecem detalhe e não são:

- `'extensoes.unaccent'::regdictionary` passa o dicionário **explicitamente**.
  É isso, e só isso, que permite declarar `IMMUTABLE`: medido, `unaccent(text)`
  é `STABLE` (`provolatile = 's'`), e nem coluna gerada nem índice funcional
  aceitam função `STABLE` — a mensagem é
  `ERROR: generation expression is not immutable`.
- O `REVOKE` no schema vem **antes** dos `GRANT` nominais. Invertido, o
  `REVOKE ... FROM PUBLIC` não desfaria o `GRANT` para `app_usuario`, mas a
  ordem escrita é a que se lê como intenção: fecha para todos, abre para um.
- `PARALLEL SAFE` e `STRICT` acompanham `IMMUTABLE` porque a função é pura e
  `unaccent(NULL)` não tem resposta melhor que `NULL`.

````markdown
# 0015 — busca sem acento em empresa

A maquinaria que a listagem `/empresas` consome. Desenho completo em
`docs/superpowers/specs/2026-09-09-empresas-design.md`.

**Objetos tocados fora do próprio escopo (R-015):** `empresa`, criada pela
`0014`, ganha a coluna gerada `busca`.

## Por que a extensão não serve direto

`razao_social` e `nome_fantasia` têm acento, e a busca precisa achar "São"
digitando "sao". O caminho óbvio — `unaccent(razao_social)` numa coluna gerada
ou num índice — **não compila**. Medido em 2026-09-09 no container
(`postgres:17`): `unaccent(text)` tem `provolatile = 's'`, é `STABLE`, e o
Postgres recusa com `generation expression is not immutable` na coluna gerada e
com `functions in index expression must be marked IMMUTABLE` no índice.

`unaccent` é `STABLE` porque a versão de um argumento resolve o dicionário pelo
`search_path` corrente. Passando o dicionário explicitamente
(`'extensoes.unaccent'::regdictionary`), a dependência some, e aí o invólucro
`sem_acento` pode ser declarado `IMMUTABLE`.

## Os dois `GRANT` que não estão na spec, e por que sem eles nada funciona

`sem_acento` **não** é `SECURITY DEFINER`: roda como quem chama. Com o schema
`extensoes` fechado para `PUBLIC` e nada concedido a `app_usuario`, o corpo dela
não alcança `extensoes.unaccent`. Medido, nesta ordem: sem nada,
`permission denied for schema extensoes`; com `USAGE` no schema,
`permission denied for function unaccent`; com os dois, `iluminacao sao joao`.

O `INSERT` do gestor falha do mesmo jeito, porque a expressão da coluna gerada é
avaliada com o privilégio de quem insere.

O `GRANT EXECUTE` é só na assinatura de duas entradas. `unaccent_init`,
`unaccent_lexize` e a `unaccent(text)` de um argumento continuam fechadas.

**Esta é a primeira função não-definidora concedida a `app_usuario`.** A R-014
classifica esse caso como bilhete, não catraca, e o motivo está lá: função não
definidora roda como quem chama, sujeita à RLS e aos mesmos privilégios, então
não escala nada. Ela não entra em `FUNCOES_CONCEDIDAS_A_APP_USUARIO` — aquela
lista é fechada sobre definidoras.

## Cinco `REVOKE`, e a invariante que os cobra

Função nova nasce com `EXECUTE` para `PUBLIC` (`proacl` nulo). A extensão traz
quatro funções e o invólucro é a quinta. A invariante de PUBLIC em
`invariantes.ts:136-142` varre **todo schema que não é do sistema**, então pôr a
extensão em `extensoes` não escapa dela — e é bom que não escape. É a primeira
vez que essa catraca cobra alguma coisa.

## A coluna `busca` não contém o CNPJ

Deliberado. Busca por CNPJ é exata e é condição separada no `WHERE`, nunca
`LIKE` dentro de `busca`. Jogar 14 dígitos numa coluna de `LIKE '%...%'` faria
`'1122'` casar com pedaço do CNPJ de empresa nenhuma a ver — e casaria de forma
diferente conforme o nome fantasia da vizinha, que é pior que não achar.

## Nenhum índice, ainda

Índice btree não serve para `LIKE '%texto%'`; só `pg_trgm` GIN serve. Com
milhares de linhas, varrer sequencialmente uma coluna **já calculada e gravada**
é barato — a coluna `STORED` é o que remove o custo real, que seria chamar a
função por linha em toda busca.

Gatilho registrado em `divida-tecnica.md`: consulta acima de **300 ms medidos no
banco por `EXPLAIN ANALYZE`** (não na requisição inteira, que responderia outra
pergunta — R-017), **ou** `empresa` acima de **20 mil linhas**.

## O custo da reescrita, medido antes de alguém esperar por ela

`ADD COLUMN ... GENERATED ... STORED` reescreve a tabela inteira segurando
`ACCESS EXCLUSIVE`: quem tenta ler `empresa` nesse intervalo espera. Medido em
2026-09-09 no container (`postgres:17`), com a tabela na forma da `0014` e texto
acentuado de verdade: 10 mil linhas em 129 ms, 100 mil em 792 ms, 1 milhão em
5,6 s (328 MB). Linear, ~5,6 µs por linha.

Até 100 mil linhas é sub-segundo e ninguém percebe. Acima de 500 mil (~3 s de
tabela travada) vira janela de manutenção. **A medição é em disco local no
Postgres 17; produção é Railway 18.6 com disco de rede**, então a ordem de
grandeza vale e o número exato não.

## A promessa do `IMMUTABLE` pode ser quebrada

Declarar `sem_acento` `IMMUTABLE` é prometer que o dicionário de `unaccent`
nunca muda. Se mudar — e troca de versão maior do Postgres pode mudar — a coluna
gerada fica desatualizada **em silêncio**: nada dá erro, a busca só passa a não
achar. Com produção em 18.6 e testes em 17, isso não é hipótese distante.
Limitação conhecida; o conserto é recalcular a coluna, e é barato **se alguém
souber que precisa**.
````

```ts
import { normalizarCnpj } from './cnpj'

export const POR_PAGINA = 50

// Um termo de busca não é um documento. O corte existe para o parâmetro que vai
// ao banco ter tamanho conhecido, não para proteger o LIKE.
export const MAX_TERMO = 100

export type Consulta = {
  // O que a pessoa digitou: volta no campo de busca e nos links de paginação.
  termo: string
  // O mesmo termo com os metacaracteres de LIKE escapados: é este que vai ao SQL.
  padrao: string
  // Não nulo só quando o termo é um CNPJ inteiro. Vira condição de igualdade.
  cnpj: string | null
  pagina: number
}

type Params = Record<string, string | string[] | undefined>

function primeiro(valor: string | string[] | undefined): string {
  if (Array.isArray(valor)) return valor[0] ?? ''
  return valor ?? ''
}

// `%`, `_` e a própria `\` são metacaracteres de LIKE. Sem escapar, digitar `%`
// na busca casa a base inteira. A barra vem primeiro, senão ela escaparia as
// barras que este próprio replace acabou de inserir.
export function escaparLike(termo: string): string {
  return termo.replace(/\\/g, '\\\\').replace(/[%_]/g, '\\$&')
}

export function lerConsulta(params: Params): Consulta {
  const termo = primeiro(params.q).trim().slice(0, MAX_TERMO)
  const pagina = Number(primeiro(params.pagina))
  return {
    termo,
    padrao: escaparLike(termo),
    // normalizarCnpj devolve null para tudo que não tem os 14 caracteres, então
    // '1122' não vira condição nenhuma — e é assim que a busca por CNPJ fica
    // exata sem depender de o SQL se lembrar disso.
    cnpj: normalizarCnpj(termo),
    pagina: Number.isInteger(pagina) && pagina >= 1 ? pagina : 1,
  }
}

export function totalDePaginas(total: number): number {
  return Math.max(1, Math.ceil(total / POR_PAGINA))
}
```

```ts
// O banco guarda normalizado (14 caracteres, só dígitos no telefone) porque a
// mesma empresa digitada com espaçamento diferente não pode virar duas.
// Formatar só na saída é o outro lado da mesma decisão: nada daqui volta para o
// banco.
export function formatarCnpj(cnpj: string): string {
  if (!/^[0-9A-Z]{12}[0-9]{2}$/.test(cnpj)) return cnpj
  return `${cnpj.slice(0, 2)}.${cnpj.slice(2, 5)}.${cnpj.slice(5, 8)}/${cnpj.slice(8, 12)}-${cnpj.slice(12)}`
}

export function formatarTelefone(telefone: string): string {
  if (/^[0-9]{11}$/.test(telefone)) {
    return `(${telefone.slice(0, 2)}) ${telefone.slice(2, 7)}-${telefone.slice(7)}`
  }
  if (/^[0-9]{10}$/.test(telefone)) {
    return `(${telefone.slice(0, 2)}) ${telefone.slice(2, 6)}-${telefone.slice(6)}`
  }
  return telefone
}
```

```ts
import { comoUsuario } from '../../server/db/como-usuario'
import { POR_PAGINA, type Consulta } from './consulta'
import type { Falha } from './repositorio'

export type EmpresaNaLista = {
  id: string
  cnpj: string
  razaoSocial: string
  nomeFantasia: string | null
  telefone: string
  email: string | null
  // Os três estados de endereço, separados de propósito: com cidade, com CEP
  // que a base não resolveu, e sem CEP nenhum. A tela diz coisas diferentes
  // para cada um — é a lição de "Fatia empresas: o terceiro estado do CEP".
  cep: string | null
  localidade: string | null
  uf: string | null
}

export type ResultadoListagem = { ok: true; linhas: EmpresaNaLista[]; total: number } | Falha

type LinhaCrua = {
  id: string
  cnpj: string
  razao_social: string
  nome_fantasia: string | null
  telefone: string
  email: string | null
  cep: string | null
  localidade: string | null
  uf: string | null
  total: string
}

// Uma consulta só. `count(*) OVER ()` traz o total do filtro junto com a
// página, em vez de uma segunda ida ao banco que responderia outra pergunta num
// instante diferente.
//
// `ORDER BY` termina em `id` de propósito: duas empresas com a mesma razão
// social deixam a ordem indefinida entre um LIMIT/OFFSET e o seguinte, e a
// página 2 repete ou pula linha. Desempate estável é o que faz a paginação
// valer alguma coisa.
//
// `ESCAPE '\'` com o termo já escapado em consulta.ts: sem isso, `%` digitado
// casa a base inteira.
//
// O corte é no banco, não no Node: com milhares de linhas, trazer tudo para
// filtrar em memória é o erro que a paginação existe para não cometer.
const SQL = `SELECT e.id, e.cnpj, e.razao_social, e.nome_fantasia, e.telefone, e.email, e.cep,
                    c.localidade, c.uf, count(*) OVER () AS total
               FROM empresa e
               LEFT JOIN cep c ON c.cep = e.cep
              WHERE $1::text = ''
                 OR e.busca LIKE '%' || sem_acento($1::text) || '%' ESCAPE '\\'
                 OR e.cnpj = $2::text
              ORDER BY e.razao_social, e.id
              LIMIT $3 OFFSET $4`

export async function listarEmpresas(gestorId: string, consulta: Consulta): Promise<ResultadoListagem> {
  try {
    return await comoUsuario(gestorId, async (executar) => {
      const r = await executar<LinhaCrua>(SQL, [
        consulta.padrao,
        consulta.cnpj,
        POR_PAGINA,
        (consulta.pagina - 1) * POR_PAGINA,
      ])
      return {
        ok: true as const,
        // count(*) OVER () vem como bigint, que o pg entrega em texto. Sem
        // linha nenhuma não há janela, e o total é zero.
        total: r.linhas.length > 0 ? Number(r.linhas[0].total) : 0,
        linhas: r.linhas.map((l) => ({
          id: l.id,
          cnpj: l.cnpj,
          razaoSocial: l.razao_social,
          nomeFantasia: l.nome_fantasia,
          telefone: l.telefone,
          email: l.email,
          cep: l.cep,
          localidade: l.localidade,
          uf: l.uf,
        })),
      }
    })
  } catch (erro) {
    // Único sinal de negócio que esta consulta produz: papel trocado entre a
    // guarda da página e a consulta. O resto é infraestrutura e sobe como
    // exceção.
    if ((erro as { code?: string })?.code === '42501') return { ok: false, motivo: 'sem_permissao' }
    throw erro
  }
}
```

```tsx
import Link from 'next/link'

// URLSearchParams e não template: o termo pode ter acento, espaço e `&`, e
// montar a query à mão é como se perde a busca ao virar a página.
function endereco(termo: string, pagina: number): string {
  const params = new URLSearchParams()
  if (termo) params.set('q', termo)
  params.set('pagina', String(pagina))
  return `/empresas?${params.toString()}`
}

export function Paginacao({ pagina, paginas, termo }: { pagina: number; paginas: number; termo: string }) {
  if (paginas <= 1) return null
  return (
    <nav className="flex items-center justify-between text-sm">
      {pagina > 1 ? (
        <Link href={endereco(termo, pagina - 1)} className="underline">
          Anterior
        </Link>
      ) : (
        <span className="text-neutral-400">Anterior</span>
      )}
      <span>
        Página {pagina} de {paginas}
      </span>
      {pagina < paginas ? (
        <Link href={endereco(termo, pagina + 1)} className="underline">
          Próxima
        </Link>
      ) : (
        <span className="text-neutral-400">Próxima</span>
      )}
    </nav>
  )
}
```
