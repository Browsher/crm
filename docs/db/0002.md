# 0002 — funções de acesso

**O que cria.** `usuario_atual()`, `pode_ler()`, `eh_gestor()`. Todas
`LANGUAGE sql STABLE SECURITY DEFINER SET search_path = ''`. `REVOKE EXECUTE
FROM PUBLIC`, `GRANT EXECUTE TO app_usuario`.

**Por quê.**

- `usuario_atual()` lê `current_setting('app.usuario_id', true)` com
  `NULLIF(..., '')` para virar NULL quando não há identidade. É a única função
  que sabe de onde a identidade vem.
- `SECURITY DEFINER` roda como dono de `usuario`, para quem RLS não vale.
  Evita recursão: a política de `usuario` chama uma função que consulta
  `usuario`. Precondição: `usuario` nunca recebe `FORCE ROW LEVEL SECURITY`,
  ou a recursão volta. É invariante automatizada em
  `src/server/db/migracoes/invariantes.ts`.
- `STABLE` evita reavaliação por linha em toda política.
- `search_path = ''` obriga qualificar `public.usuario` e fecha sequestro de
  esquema.
- `COALESCE(..., false)` porque NULL em política não nega.
- `REVOKE FROM PUBLIC`: o padrão do Postgres concede EXECUTE a PUBLIC. Sem o
  REVOKE, qualquer papel executaria.
- Sem `pode_escrever()`: sem a marca de senha provisória seria idêntica a
  `pode_ler()`. Entra na fatia de login.

**Depende de.** 0001 (`usuario`).
